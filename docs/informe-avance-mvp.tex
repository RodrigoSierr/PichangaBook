\section{Resumen del Avance del MVP}

En este informe presentamos las evidencias actuales del Producto Mínimo Viable (MVP) de \textbf{PichangaBook Arequipa} (repositorio \texttt{github.com/RodrigoSierr/PichangaBook}). El monorepo integra tres carpetas: \texttt{/backend-nestjs} (API REST y WebSockets en NestJS con PostgreSQL), \texttt{/web-admin-tailwind} (panel web para dueños de complejos) y \texttt{/mobile-flutter} (pantallas en Flutter/Dart junto al cliente móvil interactivo de demostración). En esta entrega se encuentran implementados el esquema relacional de 13 tablas, la prevención de reservas cruzadas con índices GiST, la sincronización en tiempo real por Socket.io, el cálculo de distancias con Haversine y el chat interno con redacción de teléfonos; mientras que los cobros de pasarela (Culqi/Yape/Plin), el código OTP por SMS, el número proxy y la firma de subida de videos operan actualmente mediante adaptadores de demostración locales cuya integración con servicios externos reales está programada para la siguiente semana.

\section{Diagramas del Sistema}

\subsection{Diagrama de Arquitectura Backend--Frontend}

El sistema sigue una arquitectura cliente-servidor en tiempo real configurada en \texttt{src/app.module.ts}. Tanto el panel web de los dueños (\texttt{/web-admin-tailwind}) como la aplicación móvil de los organizadores (\texttt{/mobile-flutter}) se comunican con el servidor \textbf{NestJS} mediante endpoints REST (\texttt{/api/*}) y un canal persistente de \textbf{WebSockets (Socket.io)} gestionado por \texttt{BookingsGateway} y \texttt{RealtimeBus}. El backend consta de \texttt{AuthModule} (\texttt{AuthService} + \texttt{OtpService} en memoria + JWT), \texttt{ComplexesModule} (\texttt{ComplexesService} + \texttt{AvailabilityService}), \texttt{BookingsModule} (\texttt{BookingsService} + \texttt{BookingsGateway}), \texttt{SubstitutesModule}, \texttt{IntegrationsModule} (\texttt{CulqiService} en modo demo \texttt{chr\_demo\_*}, \texttt{MapsService} con Haversine local, \texttt{MediaService} con firma \texttt{LOCAL\_DEMO}) y \texttt{DatabaseModule} (PostgreSQL con \texttt{pg Pool} / \texttt{PGlite WASM}).

\subsection{Diagrama Entidad-Relación de la Base de Datos (PostgreSQL)}

El esquema relacional definido en \texttt{backend-nestjs/schema.sql} comprende \textbf{13 tablas independientes} y la vista \texttt{v\_complex\_ratings}:
\begin{enumerate}
  \item \texttt{districts} (\texttt{PK code VARCHAR(32)}, \texttt{UQ name}, \texttt{lat}, \texttt{lng}, \texttt{is\_key\_zone}).
  \item \texttt{users} (\texttt{PK id UUID}, \texttt{full\_name}, \texttt{role}, \texttt{UQ phone\_e164}, \texttt{phone\_masked GENERATED}, \texttt{phone\_verified\_at}, \texttt{trust\_score}).
  \item \texttt{complexes} (\texttt{PK id UUID}, \texttt{FK owner\_id -> users.id}, \texttt{FK district\_code -> districts.code}, \texttt{UQ ruc CHAR(11)}, \texttt{verification\_status}, \texttt{lat}, \texttt{lng}).
  \item \texttt{courts} (\texttt{PK id UUID}, \texttt{FK complex\_id -> complexes.id}, \texttt{name}, \texttt{surface}, \texttt{players\_per\_side}, \texttt{price\_cents}, \texttt{price\_peak\_cents}, \texttt{open\_hour}, \texttt{close\_hour}).
  \item \texttt{bookings} (\texttt{PK id UUID}, \texttt{FK court\_id -> courts.id}, \texttt{FK organizer\_id -> users.id}, \texttt{channel}, \texttt{status}, \texttt{payment\_mode}, \texttt{starts\_at}, \texttt{ends\_at}, con restricción \texttt{EXCLUDE USING gist}).
  \item \texttt{booking\_events} (\texttt{PK id BIGSERIAL}, \texttt{FK booking\_id -> bookings.id}, \texttt{FK complex\_id -> complexes.id}, \texttt{FK actor\_id -> users.id}, \texttt{event\_type}, \texttt{payload JSONB}).
  \item \texttt{reviews} (\texttt{PK id UUID}, \texttt{FK complex\_id -> complexes.id}, \texttt{FK user\_id -> users.id}, \texttt{rating SMALLINT 1..5}, \texttt{comment}).
  \item \texttt{split\_payments} (\texttt{PK id UUID}, \texttt{UQ,FK booking\_id -> bookings.id}, \texttt{FK organizer\_id -> users.id}, \texttt{total\_slots}, \texttt{paid\_slots}, \texttt{UQ share\_token}, \texttt{status}).
  \item \texttt{payment\_shares} (\texttt{PK id UUID}, \texttt{FK split\_payment\_id -> split\_payments.id}, \texttt{FK payer\_user\_id -> users.id}, \texttt{payer\_name}, \texttt{method}, \texttt{UQ provider\_charge\_id}, \texttt{amount\_cents}).
  \item \texttt{substitute\_profiles} (\texttt{PK id UUID}, \texttt{UQ,FK user\_id -> users.id}, \texttt{FK district\_code -> districts.code}, \texttt{position}, \texttt{punctuality\_score}, \texttt{clip\_url}, \texttt{clip\_duration\_s BETWEEN 15 AND 30}).
  \item \texttt{substitute\_invitations} (\texttt{PK id UUID}, \texttt{FK substitute\_id -> substitute\_profiles.id}, \texttt{FK organizer\_id -> users.id}, \texttt{FK booking\_id -> bookings.id}, \texttt{status}).
  \item \texttt{contact\_relays} (\texttt{PK id UUID}, \texttt{FK booking\_id -> bookings.id}, \texttt{FK user\_a\_id -> users.id}, \texttt{FK user\_b\_id -> users.id}, \texttt{proxy\_number}, \texttt{expires\_at}).
  \item \texttt{relay\_messages} (\texttt{PK id BIGSERIAL}, \texttt{FK relay\_id -> contact\_relays.id}, \texttt{FK sender\_id -> users.id}, \texttt{body VARCHAR(500)}, \texttt{was\_redacted BOOLEAN}).
\end{enumerate}

En el flujo de acceso (Figura 13), \texttt{POST /api/auth/otp/request} genera un código OTP de 6 dígitos en memoria (\texttt{OtpService}) y, al estar activo \texttt{demoMode}, lo devuelve como \texttt{devCode} en pantalla sin enviar aún un SMS real; luego \texttt{POST /api/auth/otp/verify} registra o actualiza al usuario en la tabla \texttt{users} con su rol (\texttt{ORGANIZER} u \texttt{OWNER}) y emite el JWT. Por su parte, al convocar a un suplente en \texttt{POST /api/substitutes/:id/invite} (Figura 14) se crea una sesión en \texttt{contact\_relays} con un \texttt{proxy\_number} \textbf{simulado} (no conectado aún a una central VoIP real) y un chat interno en \texttt{relay\_messages} (\texttt{POST /api/relays/:id/messages}) que oculta automáticamente cualquier teléfono o correo escrito en el mensaje (\texttt{redactContactInfo}) y muestra solo la columna generada \texttt{phone\_masked} (\texttt{+51 9•• ••• 101}).
